\section{Vis{\~a}o Arquitetural Atual -- AS-IS}

O Poshboard {\'e} um sistema de gest{\~a}o acad{\^e}mica para programas de p{\'o}s-gradua{\c c}{\~a}o. A arquitetura atual combina backend Python/FastAPI, frontend React/Vite e persist{\^e}ncia principal em Firebase Realtime Database (RTDB).

\begin{verbatim}
Usuario
  |
  v
Frontend React/Vite - apresentacao/
  |                 \
  |                  \ fallback direto via REST
  v                   v
Backend FastAPI       Firebase RTDB
functions/main.py       ^
  |                     |
  v                     |
Rotas, services,        |
repositories e ingest   |
  |                     |
  v                     |
Firebase Admin SDK -----+
  |
  +--> APIs externas de metadados academicos
       OpenAlex, ORCID, Crossref, Semantic Scholar
\end{verbatim}

\subsection{Principais Achados Arquiteturais}

\begin{itemize}
  \item O Firebase RTDB {\'e} a depend{\^e}ncia mais cr{\'i}tica: aparece no backend, nos reposit{\'o}rios, em services e como fallback em telas do frontend.
  \item A camada \texttt{functions/common/dbref.py} reduz parte do acoplamento, mas n{\~a}o elimina chamadas diretas a \texttt{firebase\_admin.db}.
  \item O frontend deveria consumir somente a API, mas ainda possui URLs diretas para \texttt{*.firebaseio.com}.
  \item O projeto depende de APIs externas para enriquecimento bibliogr{\'a}fico; se essas APIs falham, ingest{\~a}o e atualiza{\c c}{\~a}o autom{\'a}tica ficam degradadas.
  \item A documenta{\c c}{\~a}o e os arquivos de infraestrutura est{\~a}o parcialmente divergentes: \texttt{firebase.json} aponta para \texttt{public}, enquanto o README descreve \texttt{apresentacao/dist}; workflows usam \texttt{metaorganizer-project}, enquanto \texttt{.firebaserc} aponta para \texttt{poshbard}.
  \item A documenta{\c c}{\~a}o arquitetural mistura estado atual e alvo: \texttt{docs/ARCHITECTURE.md} descreve Firestore, Firebase Authentication e Cloud Run Jobs, enquanto o c{\'o}digo atual ainda usa RTDB.
\end{itemize}

\section{{\'I}ndices Calculados}

\subsection{Crit{\'e}rios}

\begin{itemize}
  \item \textbf{IDC:} m{\'e}dia do risco das 9 depend{\^e}ncias externas/operacionais principais.
  \item \textbf{CLSn:} m{\'e}dia dos pesos normalizados das severidades: Cr{\'i}tica = 1,00; Alta = 0,80; Moderada = 0,60; Baixa = 0,20.
  \item \textbf{IP:} m{\'e}dia das notas de portabilidade, de 1 a 5, normalizada por 5.
  \item \textbf{SSQMScore:} pontua{\c c}{\~a}o do checklist dividida por 90.
  \item \textbf{IDAN:} m{\'e}dia entre depend{\^e}ncia cr{\'i}tica, smells, falta de portabilidade e falta de soberania.
\end{itemize}

\[
IDAN = \frac{IDC + CLSn + (1 - IP) + (1 - SSQMScore)}{4}
\]

\section{Arquitetura Alvo -- TO-BE}

A arquitetura alvo recomendada preserva FastAPI, React, organiza{\c c}{\~a}o em rotas/reposit{\'o}rios e ingest{\~a}o modular, mas substitui depend{\^e}ncias propriet{\'a}rias por portas/adaptadores e armazenamento mais port{\'a}vel.

\begin{verbatim}
Usuario
  |
  v
Frontend React/Vite
  |
  v
API/BFF FastAPI
  |
  +--> Application services
  |      |
  |      +--> Portas de repositorio
  |      +--> Portas de ingestao externa
  |      +--> Portas de autenticacao
  |
  +--> Adaptador PostgreSQL
  +--> Adaptador cache/filas
  +--> Adaptadores OpenAlex/ORCID/Crossref/Semantic Scholar
  +--> Exportacao/backup em formatos abertos
\end{verbatim}

\begin{longtable}{p{0.20\textwidth} p{0.25\textwidth} p{0.30\textwidth} p{0.17\textwidth}}
\toprule
\textbf{{\'A}rea} & \textbf{AS-IS} & \textbf{TO-BE recomendado} & \textbf{Ganho} \\
\midrule
\endhead
Persist{\^e}ncia & Firebase RTDB & PostgreSQL como base can{\^o}nica, export JSON/CSV e migrations versionadas. & Reduz lock-in de dados. \\
Acesso a dados & SDK Firebase em v{\'a}rias camadas & Interfaces de reposit{\'o}rio e adaptadores substitu{\'i}veis. & Permite trocar banco. \\
Frontend & API e fallback RTDB & Frontend consome somente API. & Remove acoplamento do cliente. \\
Ingest{\~a}o & Chamadas diretas a APIs externas & Jobs/filas com cache, retries, rate limiting e snapshots. & Aumenta continuidade. \\
Credenciais & Google ADC/service account & Secrets independentes do provedor; opcional Keycloak. & Reduz depend{\^e}ncia Google. \\
Deploy & Firebase Hosting e GitHub Actions & Container Docker em VPS, Kubernetes, Cloud Run ou ambiente h{\'i}brido. & Aumenta reproducibilidade. \\
CI/CD & GitHub Actions espec{\'i}fico & Pipeline port{\'a}vel documentado. & Reduz plataforma {\'u}nica. \\
Observabilidade & N{\~a}o evidenciada & Logs, m{\'e}tricas, backups testados e health checks. & Aumenta auditoria. \\
\bottomrule
\end{longtable}

\section{Respostas Objetivas Esperadas}

\subsection{Qu{\~a}o dependente o sistema {\'e} de fornecedores externos?}

O sistema tem depend{\^e}ncia relevante de fornecedores externos. O IDAN calculado foi 0,55, dentro da faixa 0,4--0,6. A depend{\^e}ncia n{\~a}o {\'e} cr{\'i}tica para todo o stack, pois FastAPI, React e bibliotecas centrais s{\~a}o abertas, mas {\'e} alta na camada de dados e opera{\c c}{\~a}o por causa do Firebase/Google.

\subsection{Quais s{\~a}o os principais riscos de lock-in?}

\begin{enumerate}
  \item Firebase RTDB como banco principal.
  \item Firebase Admin SDK usado diretamente fora de um adaptador {\'u}nico.
  \item Frontend acessando RTDB diretamente como fallback.
  \item Credenciais e opera{\c c}{\~a}o vinculadas ao Google ADC/service account.
  \item Deploy/hosting em Firebase com configura{\c c}{\~a}o divergente.
  \item Ingest{\~a}o dependente de APIs externas sem cache/snapshot robusto.
\end{enumerate}

\subsection{Qual o n{\'i}vel atual de soberania tecnol{\'o}gica?}

O SSQMScore {\'e} 39/90, ou 43,3\%, classificando o projeto como N{\'i}vel 3 -- Depend{\^e}ncia Moderada. A leitura qualitativa {\'e}: soberania boa no c{\'o}digo-fonte e no stack aberto de aplica{\c c}{\~a}o, mas soberania fraca em dados, opera{\c c}{\~a}o e infraestrutura.

\subsection{Quais depend{\^e}ncias devem ser removidas primeiro?}

\begin{enumerate}
  \item Acesso direto do frontend ao RTDB.
  \item Chamadas diretas a \texttt{firebase\_admin.db} fora dos reposit{\'o}rios.
  \item Firebase RTDB como armazenamento can{\^o}nico.
  \item Firebase Hosting/deploy espec{\'i}fico.
  \item Depend{\^e}ncia sem cache das APIs acad{\^e}micas externas.
\end{enumerate}

\subsection{Qual arquitetura futura aumenta a autonomia operacional?}

A arquitetura alvo mais adequada {\'e} uma API FastAPI com portas/adaptadores, frontend consumindo somente a API, banco can{\^o}nico PostgreSQL, jobs de ingest{\~a}o desacoplados e deploy containerizado. Firebase pode permanecer temporariamente como adaptador legado durante a migra{\c c}{\~a}o, mas n{\~a}o deve continuar como modelo de dom{\'i}nio nem como canal direto do frontend.

\section{Conclus{\~a}o}

O Poshboard n{\~a}o est{\'a} preso por toda a sua tecnologia: linguagem, framework backend, frontend e bibliotecas principais s{\~a}o majoritariamente abertas e substitu{\'i}veis. O problema central de soberania est{\'a} na concentra{\c c}{\~a}o de dados, credenciais e opera{\c c}{\~a}o em Firebase/Google, somada a acessos diretos ao RTDB no backend e no frontend.

A primeira meta de evolu{\c c}{\~a}o deve ser reduzir o acoplamento antes de trocar a infraestrutura. Em termos pr{\'a}ticos: remover o RTDB do frontend, encapsular Firebase em adaptadores, criar exporta{\c c}{\~a}o de dados e preparar PostgreSQL como persist{\^e}ncia can{\^o}nica.
